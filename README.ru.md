# SemFind / AutoFind

Локальный поиск по вашим файлам и скриншотам. Один файл SQLite, без аккаунта,
без сетевых вызовов во время работы.

Окно носит имя **AutoFind** — по папке, в которой живёт проект. Python-пакет,
CLI и каталог индекса по-прежнему называются `semfind`; переименование сломало бы
все пути в документации без какой-либо функциональной выгоды.

Шапка следует намеченному макету: лесная фотография (`web/fon.jpg`) как фон,
логотип в левом верхнем углу, поле поиска с кнопкой очистки в правом верхнем,
а фильтр по типам — рядом «таблеток» прямо под заголовком. Фото не ограничено
шапкой — это фон всей страницы (фиксированный, `cover`), с одной вертикальной
вуалью поверх всего окна и полупрозрачными стеклянными панелями сверху, так что
результаты лежат *на* изображении, и оно просвечивает в промежутках, вместо того
чтобы быть отрезанным чёрным списком. Акцент — бело-серый: оранжевая кнопка
читалась как предупреждение на фоне тумана.

## Статус

Все четыре слоя плана реализованы и работают на обычной машине с Windows
без скачивания моделей:

| Слой | Состояние | Что внутри |
|---|---|---|
| Текст (PDF, DOCX, PPTX, XLSX, EPUB, ODT, RTF, TXT/MD, код) | работает | встроенные экстракторы, без зависимостей |
| Скриншоты: OCR | работает | 3 уровня, здесь 66 языков: пакеты Windows → PP-OCRv6 multi → PP-OCRv5 по письменностям |
| Скриншоты: визуальное сходство | работает | 228-мерный дескриптор компоновки/цвета |
| Поиск | работает | нечёткие имена + BM25 + векторы, слияние через RRF |
| Поиск по именам | работает | индекс имён в памяти, 1.7 мс на 100k имён |
| Векторы | работает | memory-mapped пакет, ~40 мс в тёплом состоянии, без матрицы на 333 МБ |
| Группировка результатов | работает | версии, одинаковые копии и серии скриншотов, раскрываются |
| Язык запросов | работает | `type:`, `ext:`, `in:`, `modified:`, `size:`, `re:`, … |
| Естественный язык | работает | детерминированный компилятор интентов RU/EN со съёмными чипами |
| Доступ для агентов | работает | MCP через stdio **и** HTTP (`semfind connect`) |
| CJK-скриншоты | работает | японский, китайский и корейский читаются через RapidOCR, а не просто повторяются |
| Живые обновления | работает | опрашивающий watcher, задержка ~2 с |
| Измерение качества | работает | `eval` с Recall@10, MRR, абляцией |
| Фильтр приватности | работает | блок-лист путей + паритет с `.gitignore`, `privacy purge` |
| Приложение | работает | нативное окно (WebView2), трей, `Ctrl+Alt+Space`, автозапуск |
| Интерфейс | работает | английский по умолчанию, русский в один клик, индекс в выдвижной панели |
| Внешний вид | работает | пять обоев или своя картинка; палитра выводится из неё |
| Личный слой | работает | закреплённые файлы, сохранённые поиски, словарь — и `import kensaku` |
| Определения в коде | работает | `sym:` по девяти семействам языков, без tree-sitter |

Два апгрейда подключаются без изменений во всём остальном:
`multilingual-e5-small` для семантических текстовых векторов и `CLIP ViT-B/32`
для поиска по изображению из текста. Пока их нет, текстовый эмбеддер лексический
(слова + символьные 4-граммы), а поиск по изображениям — только по сходству,
и интерфейс честно об этом говорит, а не притворяется.

## Быстрый старт

```bat
SemFind.bat
```

или

```bash
python run.py                 # открывает окно приложения
python run.py --browser       # тот же интерфейс во вкладке браузера, если удобнее
```

`run.py` открывает настоящее окно: со своей иконкой, своим заголовком, и оно
остаётся в трее, когда вы его закрываете. `Ctrl+Alt+Space` возвращает его
откуда угодно, а повторный запуск поднимает уже работающее окно вместо
запуска второй копии.

Чтобы сделать это постоянным — запуск вместе с Windows, в трее, без консоли:

```bash
semfind install               # запись автозапуска + ярлыки на рабочем столе и в меню «Пуск»
semfind autostart status      # на что указывает запись входа
semfind autostart off         # отменить
```

Запись входа — одно значение в `HKCU\...\Run`, поэтому она также видна в
Диспетчере задач → Автозагрузка, где её можно выключить как любую другую
программу. Запускается `pythonw.exe`, а не `python.exe`: консольное окно —
это и есть разница между приложением и скриптом.

Боковая панель перечисляет папки, которые стоит проиндексировать (Документы,
Загрузки, Рабочий стол, Скриншоты) — один клик запускает индексацию, прогресс
идёт вживую, а результаты появляются по мере добавления файлов.

Командная строка:

```bash
python -m core.cli index ~/Documents ~/Downloads ~/Pictures/Screenshots --prune
python -m core.cli watch ~/Documents ~/Downloads          # держать индекс в синхронизации
python -m core.cli search "неверный пароль при входе"
python -m core.cli search "cannot find module" --kind image
python -m core.cli search "скриншоты за прошлую неделю"   # естественный язык
python -m core.cli search 're:"TODO|FIXME" ext:py'        # грамматика запросов
python -m core.cli search "смета" --sort newest -n 20 --offset 20
python -m core.cli mcp                                     # MCP-сервер для ИИ-агентов
python -m core.cli cheat                                   # напечатать грамматику
python -m core.cli eval tests/queries/labels_demo.json --ablate --verbose
python -m core.cli doctor                                  # окружение + бюджет сборки
python -m core.cli privacy                                 # что пропустит фильтр
python -m core.cli privacy purge                           # убрать это из индекса
python -m core.cli stats
```

## Язык запросов и естественный язык

Два способа сказать одно и то же. Явная грамматика главнее — если запрос уже
содержит `key:value`, компилятор интентов его не трогает.

| Синтаксис | Значение |
|---|---|
| `type:pdf` | категория (`image`, `doc`, `sheet`, `presentation`, `code`, `video`, `archive`) или расширение |
| `ext:rs` | точное расширение |
| `in:"C:\Docs"` | только внутри этой папки (пути Windows сохраняют обратные слэши) |
| `path:src` | подстрока пути |
| `modified:<7d` | изменено в пределах окна: `1h`, `7d`, `30d`, `7d..30d` |
| `size:>2mb` | `>`, `<` или `1mb..10mb` |
| `lang:python` | семейство языков по расширению |
| `name:config` / `content:timeout` | совпадение только по имени файла / только по содержимому |
| `sym:parse_query` | определение в коде — функция, класс, структура, тип, метод |
| `re:"TODO\|FIXME"` | регулярное выражение по содержимому |
| `-node_modules` | исключить слово или папку |
| `"exact phrase"` | фраза целиком |
| `mode:exhaustive` | все совпадения, сортировка по пути, без ранжирования |
| `sort:newest` | `newest`, `oldest`, `largest`, `name` |

Обычные фразы компилируются в ту же грамматику локально, без модели:

| Вы вводите | Превращается в |
|---|---|
| `скриншоты за прошлую неделю` | `type:image modified:<7d` |
| `самые большие файлы` | сортировка по размеру |
| `3 дня назад ошибка` | `ошибка modified:4d..3d` |
| `вчерашние документы` | `type:doc modified:1d..2d` |
| `pdf про индексы` | `индексы type:pdf` |
| `screenshots from last week` | `type:image modified:<7d` |

Каждый вывод возвращается чипом над результатами со словами, которые его
породили; клик по чипу убирает эти слова и повторяет поиск. Ничего не
переписывается молча, а нераспознанная фраза ищется буквально.

## Агенты (MCP)

```bash
python -m core.cli mcp        # JSON-RPC 2.0 через stdio, только чтение
python -m core.cli connect    # сам записывает конфиг клиента
```

Инструменты: `search` (с курсорной пагинацией), `read_snippet` (с ограничением),
`index_state`, `regex_search`, `find_symbol`, `similar_images`. Только чтение
по конструкции — нет инструмента, который может открыть, переместить или
изменить что-либо. `find_symbol` — тот, которым агент пользуется чаще всего:
он отвечает файлом, строкой и самим определением, так что вопрос «где эта
функция» стоит одного вызова вместо чтения файлов, пока один не покажется
подходящим.

Два транспорта, потому что правильный зависит от клиента:

| Транспорт | Адрес | Когда |
|---|---|---|
| stdio | `semfind mcp` | Claude Desktop, Cursor — процессом владеет клиент |
| HTTP | `POST http://127.0.0.1:8765/mcp` | песочные агенты, удалённые инструменты, нет процесса для запуска |

`semfind connect` записывает запись в `claude_desktop_config.json` или
`~/.cursor/mcp.json`, сливаясь с уже существующими серверами и сохраняя
`.bak` изменённого файла. `--transport http` вместо этого записывает URL-форму
с bearer-токеном, один раз сгенерированным в `~/.semfind/mcp_token`. `--write`
нужен, чтобы действительно трогать файл; без него команда печатает diff,
чего вы и хотите в первый раз.

```bash
semfind connect                      # показать, что изменится, по всем найденным клиентам
semfind connect cursor --write       # отредактировать одного клиента
semfind connect --transport http --write
semfind connect print                # готовый для вставки JSON
```

## Как это работает

```
files ──► extractors ──┐
                       ├──► chunker ──► text embedder ──┐
screenshots ──► OCR ───┘                                ├──► index.db
                                                        │    FTS5 + vectors
screenshots ──► visual descriptor ──────────────────────┘
                                                             │
                              fuzzy names ─┐                 │
                                            ├─► RRF ─────────┘
                              BM25 ─────────┤
                              KNN  ─────────┘
```

Скриншоты попадают в ту же таблицу `chunks`, что и документы, поэтому один
запрос возвращает PDF и скриншот рядом. Каждый скриншот также получает
миниатюру и визуальный вектор, что даёт «похожие скриншоты» в интерфейсе.

**Три канала, один рейтинг.** Нечёткое совпадение имён (64-битный символьный
bloom отсеивает большую часть корпуса до запуска матчера, поэтому `rdme`
находит `README.md`), BM25 по тексту чанков и косинус по векторам чанков.
Итоговый score нормализуется в `[0, 1]`, а затем корректируется: точное имя
+0.20, префикс имени +0.15, плавная свежесть `0.10·e^(−age/7d)`, frecency
`0.08·log1p(opens)·e^(−last/14d)` по файлам, которые вы действительно
открывали, и штраф за глубину, ограниченный −0.10, чтобы файл на двенадцати
уровнях вложенности не выигрывал только за счёт формы пути. Результаты —
**на файл**, а не на чанк: документ, совпавший трижды, — одна строка со своим
лучшим сниппетом.

**Хранение.** Один файл SQLite в режиме WAL: `files`, `chunks`, `chunks_fts`
(FTS5), `images`, `vectors`, `usage`, `meta`. Векторы — float32-блобы,
перебираемые в numpy: при 50k чанков это матрица на 77 МБ и единицы
миллисекунд, так что ANN-индекс был бы преждевременным. `sqlite-vec` может
заменить `Store.knn()` без изменений у вызывающего кода.

**Индексация инкрементальная.** Неизменённые файлы пропускаются по размеру+mtime,
перемещённые — по sha256. Скриншоты дедуплицируются по sha256 до запуска OCR.
`.gitignore`, `.cursorignore` и `.semfindignore` соблюдаются во время обхода,
так что вывод сборки, который репозиторий и так игнорирует, никогда не попадает
в индекс.

**Живые обновления** (`watch`) опрашивают корни каждые 2 с вместо inotify или
ReadDirectoryChanges: один stat на файл дёшев, а опрос переживает сетевые шары
и облачные синхронизируемые папки, где нативные уведомления ненадёжны. Файл
читается только после того, как он был спокоен секунду, поэтому документ,
который сохраняют, индексируется один раз в конце. При старте watcher также
удаляет записи индекса, чьих файлов больше нет, — иначе файл, удалённый пока
приложение было закрыто, оставался бы находимым навсегда.

## Приложение

`core/app.py`. pywebview размещает тот же HTML в окне WebView2 — системный
Chromium, так что ничего не бандлится, и CSS рендерится ровно как в браузере.
Сервер работает в том же процессе на loopback: один процесс, один индекс,
один кэш векторов. Второй процесс означал бы второй порт и вторую копию
пакета, открытую одновременно.

- **Без заголовка окна.** Окно без рамки и размером в *рабочую область* рабочего
  стола, поэтому останавливается над панелью задач, а не закрывает её — часы и
  иконка трея, куда прячется это приложение, находятся там. Заголовок Windows —
  это четыре кнопки, которые интерфейс уже заменяет: ✕ в углу шапки, привязанный
  к мосту pywebview (`js_api`), а не к `window.close()`. `--windowed` возвращает
  рамку, сохранённую геометрию и изменяемый край.
- **Закрыть значит спрятать.** Окно уходит в трей; индекс и сервер остаются
  тёплыми, в чём и смысл лаунчера. Выход — явный, в меню трея. Если и трей, и
  горячая клавиша не запустились, закрытие действительно закрывает — прятать без
  способа вернуться означало бы бросить процесс.
- **`Ctrl+Alt+Space`** показывает и скрывает окно откуда угодно. `--hotkey`
  меняет комбинацию, `--no-hotkey` убирает её.
- **Второй запуск поднимает первый.** Работающее приложение пишет свой порт в
  `~/.semfind/app.port` и отвечает на `POST /api/focus`; новый процесс
  спрашивает и выходит. Блокировка экземпляра (`msvcrt.locking`, освобождаемая
  ОС при падении) — это то, что вообще не даёт появиться двум окнам с двумя
  портами.
- **Окно помнит.** Размер, позиция и состояние развёрнутости живут в
  `~/.semfind/window.json`, ограниченные текущим экраном, чтобы окно с
  большего монитора не открывалось наполовину под панелью задач. Режим без
  рамки игнорирует файл: его размер — рабочая область, а не предпочтение.
- **Тёмный заголовок и иконка приложения** через `DwmSetWindowAttribute` и
  `WM_SETICON`, для случая `--windowed`. Хост WinForms по умолчанию даёт светлый
  заголовок над почти чёрным интерфейсом, что выглядит как скриншот,
  вставленный в форму.

`tools/make_icon.py` рисует `web/icon.png` и `web/icon.ico` (16–256 px), так что
иконка воспроизводима, а не бинарник, который никто не может перегенерировать.

## Интерфейс

Две вещи в компоновке — решения, а не вкус.

**Индекс — выдвижная панель, а не колонка.** Раньше это была постоянная
колонка на 320 px справа, которая отнимала треть ширины результатов ради
четырёх панелей, читаемых один раз и затем игнорируемых до конца сессии.
Теперь она открывается поверх результатов одной кнопкой в шапке, с затемнением,
которое тоже работает как кнопка закрытия, и закрытие никогда не
перестраивает список, который вы читали. Она плавает — с отступом от края окна,
скруглённая со всех четырёх углов — поэтому читается как карточка, положенная
поверх результатов, а не как стена, прикреплённая к боку окна. Всё, что было в
колонке, по-прежнему там — счётчики, корни, состояние watch, приватность,
движки, ярлыки.

**Каждое слово — ключ.** `web/i18n.js` хранит два словаря, английский как
исходный язык, а разметка несёт атрибуты `data-i18n`; всё, что рисует `app.js`,
проходит через `t()`. Переключение языка — один вызов: он заново рендерит
статический текст, чипы, строку статуса и экран простоя из тех же данных и
запоминает выбор в `localStorage`. Английский — по умолчанию, в том числе для
машины, где Windows на русском.

Поисковый движок не владеет ни одним словом. Чип приходит с сервера как
*вид* и *значение* — `{"kind": "week"}` или `{"kind": "daysAgo", "value": "3"}`
— и интерфейс решает, как это сказать, потому что «изменено: за прошлую неделю»
— это предложение, а компилятор — не то, что знает язык читающего человека.
То же касается подсказок и значений типов. `tests/test_i18n.py` валит сборку,
если у вида нет предложения ни на одном языке, если ключ есть в одном словаре
и нет в другом или если атрибут `data-i18n` называет несуществующий ключ.

Русскому нужны три формы множественного числа, английскому — две; правило
живёт рядом со строками. `3 snapshots` и `3 снимка` получаются из одного вызова.

Фильтр дат — та же история в меньшей коробке. Нативный `<input type="date">`
рисует свой призрачный текст и открывает свой выборщик в локали *ОС*, и из
скрипта это не переопределить: английский интерфейс на русской Windows всё
равно говорил «дд.мм.гггг» и открывал русский календарь. Поэтому календарь наш
— скруглённый, серый, с понедельника, с сегодняшним днём в виде кольца и
выбранным днём в виде залитой ячейки, а названия месяцев и дней недели берутся
из того же словаря, что и всё остальное.

Шестерёнка открывает один и тот же диалог на обоих языках: выбор обоев сверху,
сегментный переключатель и список «О программе», который сообщает, чем на
самом деле является эта установка — файлы и чанки, размер базы данных, сколько
языков OCR может здесь прочитать, какие эмбеддеры загружены и версия.

### Фон — это тема

Тёмный интерфейс рядом с фотографией обычно выглядит как чёрный прямоугольник
с фото за ним. Здесь картинка *и есть* палитра: каждая поверхность —
`hsl(var(--hue) var(--sat) …)`, выборщик задаёт два числа, и панели, границы,
чипы и состояния наведения следуют за ними. Выберите коричневую стену — границы
станут тёплыми; выберите океан — станут бирюзовыми.

Когда картинка ваша, вам редко нужна она целиком. Плитка «Своё» открывает ещё
два элемента управления, скрытых для градиентов: **Position** (top / center /
bottom) фиксирует край, к которому привязан кроп, а **Zoom** (±) приближает или
отдаляет. Оба — только CSS: `background-position` и `transform: scale()` на слое
обоев, — так что изменение мгновенное и переживает перезагрузку. Оттенок всё
ещё читается из всего изображения, а не из обрезанного куска.

Это значит, что ваша картинка должна ответить на один вопрос: какого она
цвета? Среднее по RGB не может — среднее заката серое, потому что оранжевый и
синий гасят друг друга. Измерение — **круговое среднее оттенков**, взвешенное
насыщенностью и игнорирующее выцветшие пиксели:

```js
sum += saturation * sin(hue);   // оттенки — углы, поэтому складываются как векторы
cos += saturation * cos(hue);
hue = atan2(sum, cos);
```

Два меньших решения вытекают из той же идеи.

**Обои — это файл, а не запись в `localStorage`.** Фото на 4 МБ в хранилище
браузера — это ошибка квоты, ждущая не того дня, и оно умрёт при очистке кэша.
Оно пишется в `~/.semfind/background.<ext>` рядом с индексом — так оно
выживает, едет вместе с резервной копией каталога конфигурации, а
`GET /api/background` отдаёт его обратно с query для сброса кэша. Хранится
только одно за раз: новый PNG удаляет старый JPG, потому что два файла
оставили бы читателю выбор расширения, которое он случайно попробует первым.

**Первый кадр уже нужного цвета.** `app.js` выполняется в конце body — это на
одну отрисовку позже: окно мигало бы стандартным лесным фоном и затем
перескакивало на ваш. Скрипт из двенадцати строк в `<head>` читает сохранённый
выбор и задаёт `--wall`, `--hue`, `--sat`, `--wall-pos` и `--wall-scale` на
корневом элементе до того, как что-либо отрисовано. `tests/test_theme.py`
проверяет, что скрипт находится в head, что он читает тот же ключ хранилища,
который пишет `app.js`, и что каждая поверхность в стилях выводится из оттенка,
а не привязана к hex-значению.

## Что вы приносите с собой

Никто не меняет поисковое приложение из-за поиска. Люди остаются там, где они
есть, из-за двадцати закреплённых файлов, четырёх запросов, которые запускают
каждую неделю, и десяти слов, которым научили. Это дорогие вещи, и именно
из-за их потери лучший поисковый движок проигрывает худшему.

Поэтому они — часть продукта, а не запоздалая мысль:

**Закрепления.** Одна звёздочка на любом результате, и файл с этого момента
висит на экране простоя. Закрепление — бонус в рейтинге, а не фильтр: оно
поднимает файл на 0.12 — больше свежести (0.10), меньше совпадения имени
(0.15), — так что закреплённый скриншот не скрывает документ, который вы
на самом деле искали.

**Сохранённые поиски.** Закладка внутри поля поиска сохраняет запрос как
введённый, включая фильтры. Повторное сохранение того же запроса переименовывает
его вместо дублирования, а список упорядочен по тому, как часто вы его на самом
деле запускаете.

**Словарь.** `cv → резюме` в настройках, и с этого момента ввод `cv` ищет также
`резюме`. Расширение по целым словам и без учёта регистра и никогда не
срабатывает внутри пары `key:value` — `type:cv` по-прежнему означает файлы
`.cv` — и ограничено восемью заменами, чтобы плохая запись не могла растить
запрос без предела. Что сработало, показывается чипом над результатами рядом с
чипами компилятора интентов, а удаление чипа повторяет запрос без него. Слова
живут в настройках, над «О программе», с `×` в каждой строке:

**Определения.** `sym:parse_query` отвечает определением, а не файлом: сначала
точное имя, затем префикс, затем подстрока, и строка говорит
`function parse_query · line 214` с исходной строкой под ней. Девять семейств
языков распознаются по шаблону — Python, JS/TS, Rust, Go, Java/Kotlin, Ruby,
PHP, shell, SQL — потому что экстрактор без зависимостей, который прав в ~95%
определений, лучше сборки tree-sitter, которая стоит 40 МБ и шага компиляции на
Windows. Комментарии пропускаются, поэтому `# def not_real():` — не совпадение.

Все три живут в том же файле SQLite, что и индекс, в `pins`, `saved` и
`aliases`. Это значит, что они едут с резервной копией, любой SQLite-клиент
может их прочитать, и они никогда не покидают машину — что также делает
миграцию копированием, а не перенабором:

```bash
semfind import kensaku              # найти конфиг, показать, что переедет
semfind import kensaku --write      # скопировать закрепления, сохранённые поиски, словарь
semfind import kensaku "C:\Users\you\AppData\Roaming\kensaku"
```

Читатель не предполагает схему. kensaku — приложение Tauri, поэтому его
хранилище находится в одном из нескольких известных мест и имеет одну из двух
форм, JSON или SQLite; читатель обходит то, что находит, и распознаёт
закрепления, запросы и алиасы по имени. Закрепление, чей файл не в индексе,
сообщается путём, а не молча отбрасывается, потому что «проиндексируй эту папку
и запусти снова» — лучший ответ, чем избранное, которое тихо не приехало.

То же самое есть в командной строке — для скриптов и для машины, где окно не
открыто:

```bash
semfind pin "C:\Docs\contract.pdf"   # --off, чтобы открепить
semfind pins
semfind saved "type:pdf invoices" --label "Invoices"
semfind alias cv "резюме"
semfind sym parse_query -n 5
```

| 6 скриншотов + плановый документ + этот репозиторий | 36 | 174 | 0.7 с | 7–10 мс |

| Реальное дерево `~/Downloads` (Blender, SteamCMD, проекты) | 8 373 | 216 998 | ~14 мин | 21 мс |

но тот корпус весит 1.5 МБ всего, с одним чанком на файл — папки с обилием PDF
будут на порядок медленнее, потому что узкое место — извлечение, а не
эмбеддинг.

Два числа, которые план должен был знать:

- **Холодный старт раньше стоил 2.6 с** на индексе в 217k чанков: матрица
  векторов (333 МБ) читалась из SQLite и складывалась. Теперь это
  memory-mapped пакет — см. следующий раздел, — поэтому первый запрос после
  перезапуска стоит столько же, сколько второй.
- **Индекс — 1.06 ГБ на 8.4k файлов**, плюс пакет на 320 МБ. Большая часть —
  float32-векторы, а не текст. Дедупликация одинаковых чанков по всему дереву
  сократила бы его существенно.

## Масштабирование за 100k файлов

Три вещи раньше росли вместе с корпусом так, что сломались бы на 100k файлах.
Все три заменены, и каждое число ниже измерено, а не оценено.

### Имена живут в памяти, а не в SQLite

`core/nameindex.py`. Каждое имя, путь и вид один раз загружаются в плоские
массивы с 63-битным символьным bloom, и bloom-префильтр — это один
векторизованный AND по всему корпусу. Запросы на литеральную подстроку
отвечаются одним C-сканированием регулярным выражением по NUL-склеенному
буферу байтов, со скорингом в numpy — так что стоимость отслеживает число
совпадений, а не размер индекса.

| Имён | Раньше (SQL-скан) | Теперь, литерал | Теперь, аббревиатура |
|---|---|---|---|
| 8 000 | 35 мс | 0.2 мс | 1.7 мс |
| 100 000 | — | 1.7 мс | 19 мс (с потолком) |
| 1 000 000 | — | 20 мс | 45 мс (с потолком) |

Уровень аббревиатур ограничен 20k кандидатами, сначала новые, — именно это
делает его **ограниченным**, а не линейным: запрос по 1M имён стоит столько же,
сколько по 100k.

### Векторы memory-mapped, а не сложены

`core/vectors.py`. Матрица float32 на 333 МБ раньше читалась из SQLite и
копировалась в numpy-массив при старте. Теперь это упакованный побочный файл
(`index.db.v4.vec`), отображаемый в процесс: без копии, без анонимных 333 МБ, и
страницы остаются в кэше ОС между перезапусками.

| Бэкенд | Холодный старт | Запрос, 217k чанков | Доп. диск |
|---|---|---|---|
| numpy-матрица (раньше) | 2 600 мс | 21 мс | — |
| sqlite-vec `vec0` | 0 мс | 90–255 мс | +333 МБ |
| memory-mapped пакет | ~0 мс | 40 мс | +320 МБ |

`sqlite-vec` реализован и доступен (`--vector-backend sqlite-vec`), но не
является умолчанием: его точный KNN обходит теневые строки по одной и стоит в
4–12 раз больше на запрос, чем одно matmul. Пакет — чистый кэш: `vectors` в
SQLite остаётся источником истины, так что удаление файла стоит пересборки, но
никогда — данных.

Версия в имени несущая. Повышение формата, пока старый процесс ещё держал
старый файл отображённым, означало, что Windows отказывал в переименовании,
сборка выбрасывалась, и каждый текстовый запрос откатывался к чтению всех
векторов из SQLite: **2 860 мс против 12 мс**, измерено дважды подряд на
реальном индексе, прежде чем это было понято. Теперь две версии никогда не
делят файл, а сборка, которая всё ещё не может лечь на место, отдаётся из
своего временного имени вместо того, чтобы быть выброшенной. `docs/decisions.md`
§49.

### Почти-дубликаты схлопываются

`core/group.py`. Две строки, говорящие одно и то же, — одна строка со значком:

- **версии** — `resume.docx`, `resume_v2.docx`, `resume-final.docx`,
  `resume (1).docx`, `итоговый_отчет_в2.docx` группируются по нормализованному
  стеблю внутри одной папки. Консервативно намеренно: слить два действительно
  разных документа хуже, чем пропустить слияние, поэтому `report` и
  `report_2024` остаются врозь.
- **копии** — один и тот же файл, скопированный в две папки, — одна строка.
  Одно имя и один sha256, разные пути: `openWallpaper\...\steambootstrapper_russian.txt`
  и `zz\...\steambootstrapper_russian.txt` — один ответ, а не два. Одинаковые
  байты под *другим* именем остаются раздельными, потому что имя обычно и есть
  причина, по которой пользователь оставил вторую копию. На этом корпусе это
  611 строк (7%), которые раньше были шумом.
- **серии** — скриншоты одного экрана в пределах 15 минут, в одной папке, при
  **одинаковом размере в пикселях**, в пределах 10 бит 63-битного dHash **и**
  с 60% общих слов OCR. Каждое из этих условий пришло из ложного срабатывания
  на реальных данных: dHash сначала масштабирует до 9×8, поэтому слеп к
  масштабу и оценил одну иконку, экспортированную в 30, 44, 71 и 1024 px, как
  идентичную. Отсюда нижняя граница размера (640 px — скриншот это экран, а не
  кадр спрайта 32×32) и, когда ни у одной стороны нет текста OCR для
  подтверждения, почти точный хеш (≤2 бит). Неверное слияние скрывает файл;
  пропущенное оставляет лишнюю строку.

Клик по значку раскрывает группу. Значок — факт, а не украшение: он говорит,
что строка, которую вы видите, — та, которую ранжировщик выбрал из N.

Сериям нужен перцептивный хеш, пришедший в схеме v4. Индекс, собранный старой
версией, получает его дозаполнение в конце `semfind index` — только декодирование,
без OCR, 1 097 изображений за 3.8 с здесь. Без этого детектор молча не видел бы
хешей ровно у тех скриншотов, что были проиндексированы первыми, так как
неизменённый файл никогда не переиндексируется.

## Качество

`semfind eval` оценивает размеченный набор запросов. На smoke-наборе из 14
запросов по корпусу в 8.4k файлов:

| Канал | Recall@10 | MRR | p95 |
|---|---|---|---|
| Только BM25 | 0.714 | 0.620 | 22 мс |
| Только векторы (хеширующий фолбэк) | 0.071 | 0.073 | 39 мс |
| Слияние (поставляемое умолчание) | 0.714 | 0.620 | 59 мс |

Читайте это как диагноз, а не как оценку. С фолбэк-эмбеддером векторный канал
не добавляет ничего и при равном весе активно вредит (0.643 recall до
приглушения). Два изменения вышли из измерения: вес векторов теперь берётся из
самого эмбеддера (0.3 для хеширующего фолбэка, 1.0 для семантической модели), а
запрос без лексического совпадения возвращает ничего вместо хеш-коллизий.
Оставшиеся промахи — все перефразировки — «ошибка сборки» для скриншота, где
написано `Error: cannot find module`, — это ровно то, для чего нужен e5, и
именно то, чего эта сборка не умеет.

Набор приёмки из 20 запросов из плана лежит в `tests/queries/queries.json`;
метки всё ещё заглушки. Recall@10 ≥ 0.7 остаётся недоказанным, пока кто-нибудь
не запустит его на реальном корпусе с ответами, написанными вторым человеком.

## Замечания об OCR

Распознаватель Windows поставляется с ОС и знает русский, если установлен
языковой пакет — без бинарника Tesseract, без 20 МБ traineddata, без шага
установки.

Препроцессинг зависит от движка, и это измерено, а не предположено: прогон
тёмного скриншота через grayscale + autocontrast **снижает** вывод движка
Windows (136 против 162 символов на одном и том же изображении), потому что он
нативно обрабатывает тёмные темы. Поэтому он получает изображение как есть плюс
апскейл для мелкого текста; только Tesseract получает обработку
grayscale-and-invert.

Порядок движков: `windows-ocr` → `tesseract-cli` → `pytesseract` → `rapidocr`.
Движок, породивший текст скриншота, записывается в индекс, так что позднейшее
переключение видно, а не молчаливо.

**66 языков.** Три уровня, и порядок — это и есть дизайн:

| Уровень | Движок | Языки | Стоимость |
|---|---|---|---|
| 1 | Windows OCR, *каждый* установленный пакет | здесь `ru`, `en-US` | 6–60 мс |
| 2 | rapidocr PP-OCRv6 `multi` | 53: все латинские, японский, китайский | ~1.9 с |
| 3 | rapidocr PP-OCRv5 по письменностям | корейский, арабский, кириллица, деванагари, греческий, тайский, тамильский, телугу | ~1.2 с каждый |

Уровень 1 пробует каждый установленный языковой пакет, а не язык отображения:
на этой машине `en-US` читает русский как `npl'1BeT`, а пакет `ru` читает его
правильно, за те же 10 мс. Уровни 2 и 3 запускаются только когда результат
неправдоподобно мал для количества краски в изображении — тот же измеренный
порог, что и раньше, — так что русский скриншот стоит 10 мс, а японский — 2 с
вместо того, чтобы быть проиндексированным как случайные латинские буквы.

Измерено сквозным образом на отрендеренных тестовых изображениях:

| Изображение | Победивший движок | Время | Текст |
|---|---|---|---|
| Английский | `windows-ocr` | 0.01 с | точный |
| Русский | `windows-ocr` (`ru`) | 0.01 с | точный |
| Китайский | `rapidocr:multi` | 2.0 с | `你好世界 中文测试` |
| Японский | `rapidocr:multi` | 3.4 с | `こんにちは世界 日本語のテスト` |
| Корейский | `rapidocr:korean` | 5.3 с | `세계 … 테스트` |
| Арабский | `rapidocr:arabic` | 7.2 с | арабская письменность, частично верно |

Хвост дорог намеренно и ограничен двумя способами. Модели, которых нет на
диске, никогда не скачиваются посреди прогона индексации — `semfind ocr
download all` забирает их один раз (9 моделей, 70 МБ). И цепочка отключает себя
после восьми подряд попыток, ничего не изменивших, так что папка с фотографиями
перестаёт платить за фолбэк примерно через 10 с, а папка с японскими
скриншотами — где каждая попытка успешна — никогда не достигает предела.

`semfind ocr languages` печатает языки, читаемые *прямо сейчас*, с их
приветствиями; `semfind doctor` печатает счётчик, модели на диске и
установленные пакеты. `ocr_cjk_model` по-прежнему закрепляет свою модель
распознавания.

## Холодный старт

`tools/coldstart.py` запускает настоящее приложение и опрашивает, пока индекс не
прогреется, замеряя три отдельных рубежа. Три прогона, медиана:

| Рубеж | Медиана | Что значит |
|---|---|---|
| порт отвечает | 0.65 с | Python поднялся, поток сервера работает |
| индекс готов | 0.77 с | пакет векторов подгружен — `/api/ready` переключается |
| окно видно | 0.96 с | окно без рамки с заголовком AutoFind на экране |
| первый поиск | 148 мс | один запрос по уже тёплому индексу |

Разрыв между «порт отвечает» и «индекс готов» — 120–160 мс предпрогрева;
остальное — старт интерпретатора плюс `import webview`, что не убирает никакая
наша оптимизация. Разрыв между «индекс готов» и «окно видно» — это WebView2,
рисующий свой первый кадр.

Настоящий холодный старт требует ещё и сброса кэша страниц ОС, для чего нужны
права администратора; здесь измеряется старт с индексом на диске и
полутёплым файловым кэшем. Цитировать нужно медиану нескольких прогонов.

## Экран загрузки

Поскольку окно рисуется ~190 мс после того, как индекс уже тёплый, заставка не
прикрывает медленную загрузку — она существует, чтобы первым на экране была не
пустая сетка. Она показывает одно приветствие, меняющееся каждые 700 мс,
взятое из языков, которые OCR этой машины действительно может прочитать:
**языки на экране — ровно те, на которых индекс может найти текст.** На этой
машине их 66, поэтому приветствие с равной вероятностью может быть `こんにちは`,
`안녕하세요` или `Hello`.

Оно ограничено с обеих сторон — минимум 900 мс, чтобы никогда не мигать,
максимум 8 с опроса, чтобы никогда не зависнуть, — а Escape или клик его
закрывают. Диплинк (`?q=` или `?preview=`) его пропускает: ссылка на файл — не
запрос приветствия.

## Эмбеддеры

| Роль | По умолчанию | Апгрейд |
|---|---|---|
| Текст | `hashing-384` (слова + символьные 4-граммы) | `e5-small` int8 ONNX |
| Визуал | `layout-228` (цвет, компоновка, края) | `CLIP ViT-B/32` int8 ONNX |

Положите веса и перезапустите:

```
~/.semfind/models/e5-small/model.onnx + tokenizer.json
~/.semfind/models/clip/visual.onnx + textual.onnx + tokenizer.json
```

`pip install 'semfind[onnx]'` добавляет рантайм. Индекс записывает, какой
эмбеддер его построил, и отказывается смешивать два, так что переключение
означает переиндексацию — намеренно, а не по недосмотру.

## Бюджет сборки

`semfind doctor` складывает то, что действительно поставлялось бы:

```
bundle       378.0 MB of 150 MB budget  over by 228.0 MB
  python-embed                  15.0 MB   runtime
  numpy                         18.0 MB   runtime
  pillow                         4.0 MB   runtime
  winrt bindings                 3.0 MB   runtime
  onnxruntime                   50.0 MB   optional: only with e5/CLIP
  app code + web                 1.0 MB   runtime
  model:e5-small               120.0 MB   download or bundle
  model:clip-vit-b32            45.0 MB   download or bundle
  model:tesseract-rus-eng       22.0 MB   download or bundle
  model:argos-ru-en            100.0 MB   download or bundle
```

Установщик из плана на ≤150 МБ не может вместить e5 + CLIP + Argos. Отказ от
Argos (русским запросам тогда понадобится многоязычный экспорт CLIP, или
поиск текст→изображение останется только английским) экономит 100 МБ и всё
равно оставляет 278 МБ. Реалистичное разделение — оболочка ~60 МБ плюс модели,
скачиваемые при первом запуске, либо жёсткий выбор между семантическим текстом
и текст→изображение.

## Приватность

Два отдельных обещания, и второго не хватало:

1. **Ничего не покидает машину.** Никаких сетевых вызовов во время работы;
   HTTP-сервер привязан к 127.0.0.1 и отвергает чужие заголовки Host.
2. **Кое-что никогда не попадает в индекс.** `core/privacy.py` отбрасывает
   хранилища паролей, ключевой материал, данные профилей браузеров и папки
   облачных учётных данных *до* того, как открыт какой-либо файл: `.ssh`,
   `*.kdbx`, `wallet.dat`, каталоги профилей Chrome/Edge, `*.env`, имена вида
   `*password*`. Исходные файлы освобождены от широких glob-шаблонов имён —
   Blender поставляет `secrets.py`, и индексация модуля стандартной библиотеки
   не является инцидентом.

Фильтр включён по умолчанию, его счётчик появляется в выводе `index` и в
интерфейсе, а `semfind privacy purge` удаляет то, что просочилось раньше. На
этой машине он нашёл два файла «Пароль на архив», которые старше фильтра.

Всё ещё отсутствует: **индекс не зашифрован**. Отфильтрованные пути
пропускаются, но всё остальное — включая OCR-текст всего вашего экрана — лежит
в простом файле SQLite. Блок-лист на уровне приложения, переключатель паузы и
SQLCipher — открытые пункты.

## Ещё не сделано

- Веса `CLIP` и `e5` не бандлятся; бюджет установщика — 378 МБ против 150 МБ
  из плана, и это решение всё ещё открыто.
- Шифрование индекса, блок-лист приложения и глобальный переключатель паузы OCR.
- Два языка интерфейса. Словари — это механизм, а не покрытие: третий язык —
  это таблица и строка в `LANGUAGES`, но никто его не написал.
- Подписанный установщик: окно приложения, трей, горячая клавиша и ярлыки есть,
  но MSI и подписи кода пока нет, так что «установить» — это команда, а не
  мастер.
- Счётчики фасетов вычисляются для запросов только с фильтрами, а не для
  ранжированных — пул кандидатов ограничен, так что число было бы ложью.
- OCR покрывает 66 языков на этой машине; остальная таблица rapidocr
  (иврит, бенгальский, грузинский, армянский) требует языкового пакета Windows,
  который может добавить только установщик ОС.
- Холодный старт — 0.77 с до тёплого индекса, из которых ~0.65 с — старт
  интерпретатора и `import webview`. Чтобы уйти ниже, нужен упакованный
  бинарник, а не более быстрый Python.
- Сам документ всё ещё содержит несоответствия, перечисленные в ревью
  (таблица top-10 против цифры, p95 против медианы, 30 ноя против 29 ноя).

Закрыто со времени сравнения с kensaku: индекс имён (1.7 мс на 100k вместо
35-мс скана на 8k), матрица векторов (memory-mapped пакет: ~40 мс тёплый,
~0 мс холодный, без выделения 333 МБ), группировка версий, одинаковые копии и
серии скриншотов, MCP через HTTP с `semfind connect`, OCR на 66 языках,
холодный старт меньше секунды и лаунчер — окно без рамки над панелью задач,
иконка в трее, глобальная клавиша вызова и запись входа.
