## CRITICAL

### A1. Каждое сниппет-чтение расшифровывает блоб заново
- **Где:** `core/store.py` — `_data_of` → `vault.open_bytes` (AES-GCM), `_row_slice` → `zlib.decompress`; вызывается из `Store.chunk_rows` для каждого чанка результата.
- **Почему:** file_texts контентно-адресованы, но расшифровка не кэшировалась; 50 чанков страницы = ~50 AES-открытий + inflate, при том что одни и те же документы возвращаются из запроса в запрос.
- **Критичность:** CRITICAL — измеренные ~11 ms из 38.9 ms тёплого запроса (28%).
- **Влияние:** тёплый поиск 37.7 ms vs kensaku 26.7 ms — проигрыш в 1.4×.
- **Исправление:** LRU расшифрованных блобов по hash (128 MB cap) + LRU надутых блоков по (hash, block) — **СДЕЛАНО ДО АУДИТА** (прозрачно отмечаю: изменение внесено до получения плана этапов). Замер: тёплый запрос 38.9 → **5.8 ms** (медиана, 20 повторов). Валидность кэша: hash = контентный адрес, ключ не может устареть; объём ограничен.

### A2. Мёртвый вектор-пак занимает 341 MB
- **Где:** `~/.autofind/index.db.v4.vec` (341 305 292 байт, дата 10 ноя).
- **Почему:** со схемы v9 `_setup_vectors` всегда возвращает `"filebin"` (store.py:1269-1277); `Store.pack()`/`PACKS.acquire` достижимы только при `vector_backend == "pack"` (api.py:2414 — никогда), `rebuild_pack` не имеет ни одного вызывающего. Пак писался в эпоху до filebin (упоминание «+333 MB» в store.py:1304-1307) и с тех пор никем не читается.
- **Критичность:** CRITICAL для метрики «Индекс на диске»: −341 MB мгновенно.
- **Исправление:** удалить файл; в коде — `maintenance.cleanup_stale_artifacts` должен подчищать `.v{<текущая>}.vec` и legacy `index.db.vec`/`.v3.vec` (vectors.py:635 уже имеет список кандидатов — переиспользовать).
- **Риск:** нулевой при подтверждённом filebin-бэкенде; файл пересобирается, если бэкенд pack когда-нибудь вернут.

### A3. Реликт миграции `index.v9.db` — 220 MB
- **Где:** `~/.autofind/index.v9.db` (13 873 файла — старая копия индекса).
- **Почему:** создан внешним/старым кодом (текущий код таких копий не делает — migrations живут внутри БД, maintenance.py:16-18; grep подтверждает отсутствие writers). Современный код его не читает.
- **Критичность:** CRITICAL для метрики диска: −220 MB.
- **Исправление:** удалить файл; добавить в `cleanup_stale_artifacts` правило «index.v*.db старше N дней и не равен текущему db».

## HIGH

### A4. Cold CLI: полная расшифровка `.bm25seal` на каждый запуск
- **Где:** `core/store.py` `inram_bm25` (одноразовый CLI, `ram_bm25=False`, sealed) → `_load_sealed_bm25` (store.py:2122): `read_bytes()` 145 MB → AES-GCM расшифровка всего буфера → `np.load` → `from_arrays` (полная материализация).
- **Замер:** cold CLI search ≈ 695-1385 ms (без/с профилировщиком); kensaku — 183 ms.
- **Исправление (двухчастное):**
  1. **Сегментированный sidecar**: писать плоские постинги (`flat_pos`, `flat_tfs`) сегментами по ~1-4 MB, каждый сегмент шифруется отдельно (свой nonce), файл маппится (file-backed → не растит USS); при поиске расшифровываются только сегменты с постингами терминов запроса + маленький заголовок. Cold падает с ~450 ms расшифровки до десятков ms; RAM — приватная память почти вся уходит из heap.
  2. Совместимость: старый monolithic `.bm25seal` читается как сейчас; новый формат пишется при `reseal_bm25`/после индексации.

### A5. Cold CLI игнорирует запущенный сервер
- **Где:** `core/cli.py::_cmd_search` всегда открывает локальный Store.
- **Почему:** kensaku Cold CLI 183 ms достигается демоном: их CLI коннектится к работающему serve. У AutoFind сервер часто уже запущен (трей/автостарт), порт лежит в `<home>/app.port` — CLI мог бы отдать результат за ~10 ms HTTP + ~150 ms загрузки интерпретатора.
- **Исправление:** в `_cmd_search` — быстрый дедлайн-коннект к `app.port` (`/api/search`), при успехе отформатировать те же строки и выйти; при недоступности — локальный путь без изменений. Флаг `--local` для обхода.
- **Влияние:** cold CLI на машине с запущенным приложением ≈ 150-250 ms.

### A6. RAM сервера: расшифрованный BM25 в private heap
- **Где:** `_load_sealed_bm25` → `InRamBM25.from_arrays` — все массивы numpy в private memory (USS).
- **Замер:** 387.4 MB USS (таблица пользователя); в моём замере основной вклад — 145 MB расшифрованных постингов + копии при np.load.
- **Исправление:** сегментированный sidecar из A4 решает это (file-backed mmap шифротекста + LRU расшифрованных сегментов с потолком ~64 MB). Дополнительно: `memguard` может сбрасывать сегментный кэш при неактивности.
- **Остаток:** interpreter+numpy+библиотеки ≈ 60-90 MB USS — ниже 52.8 MB на чистом Python не опуститься (у kensaku Rust; их 52.8 MB — serve без daemon).

### A7. WAL 112 MB
- **Где:** `~/.autofind/index.db-wal` (112 714 992 байт) при index.db 107 MB.
- **Почему:** поисковые записи (recent_searches/usage) коммитятся, чекпоинт — только на compact/close; сервер живёт неделями.
- **Критичность:** MEDIUM (диск + время восстановления).
- **Исправление:** `PRAGMA wal_checkpoint(PASSIVE)` раз в N минут в сервере (idle-поток) или после K коммитов write-Store.

### A9. Индексация: 1391 ф/с vs kensaku 4022
- **Статус:** профиль сделан, горячая точка подтверждена и частично устранена (A15).
- Постадийные замеры до native: `read 3.79 c`, `store 1.48 c`, `embed 1.16 c`,
  `sha 1.08 c`, `extract 0.56 c`, `scan 0.49 c` (4 воркера, 10k файлов).
- Fresh-path SQLite write optimization и native read/decode дали 2904–3036 ф/с;
  kensaku — 4022 ф/с. Остаток — store/embed/sha и системный syscall-флор Python.

## MEDIUM

### A8. Fingerprint проверяется после полной загрузки
- **Где:** `_load_sealed_bm25` (store.py:2122-2136): сначала читает/расшифровывает весь файл, потом сравнивает fingerprint и возвращает None.
- **Исправление:** хранить fingerprint в первых байтах sidecar (до шифрованного тела) и проверять до расшифровки; для сегментного формата A4 — в открытом заголовке (fingerprint не секрет).

### A10. `core/vectors.py` — почти мёртвый слой
- **Где:** 1170 строк pack/hot/sqlite-vec логики; активный путь — только `quantize_vector`/`dequantize_vector` для `vectors` (изображения).
- **Влияние:** поддержка + риск ошибок (это уже дало A2).
- **Исправление:** не удалять резко: пометить как legacy, вынести pack-логику в отдельный модуль `core/vectors_pack.py` с пометкой, добавить тест-маркер «pack backend is unreachable since v9». Решение об удалении — отдельно, с пользователем.

### A11–A14. Низкий приоритет
- `importers.py` — test-only, либо подключить к CLI (`import efu/listary`), либо задокументировать.
- Корень репо: `_diag.py`, `afdiag*.spec`, `build/`, `dist/` — вынести в `.gitignore`/удалить из VCS-обзора (не удалять без проверки).
- Фронтенд: app.js 3158 строк и i18n.js 1671 отдаются как есть; для локального loopback-сервера это некритично (гигабит loopback + кэш браузера), минификация даст максимум ~100-200 KB трафика и ~10-30 ms парсинга. LOW.
- `models.py`/`ocr/indra.py`: два загрузчика с одинаковыми гарантиями — объединить общий хелпер.

## Дополнение (финальное): CPython native hot path (A15)

По явной просьбе пользователя («теперь давай cpython») вместо USN Journal реализован
опциональный CPython C-extension `afnative` для самой горячей части индексации.

- **Файлы:** `native/afnative.c`, `native/build_native.py`, сборка — `python native/build_native.py`
  (на этой машине MSVC + Windows SDK; helper теперь передаёт `--force`).
- **API:** `read_text_digest(path, max_bytes) -> (str | None, bytes)` — один C-вызов делает
  `_wfopen`/`fread`, SHA-256 и ту же лестницу кодировок, что `extract_plain_bytes`;
  двухступенчатый буфер 1 MB → `max_bytes` повторяет поведение pure Python и не выделяет
  20 MB на каждый маленький файл.
- **Интеграция:** `core/indexer.py::_extract_text_job` вызывает native только для
  PLAIN_KINDS (кроме csv/tsv). Отсутствующий/старый `.pyd` или `AUTOFIND_NO_NATIVE=1`
  прозрачно возвращают управление проверенному Python-пути.
- **Эквивалентность:** 10 parametrized-тестов в `tests/test_afnative.py` — UTF-8, BOM,
  cp1251, koi8-r, latin-1, binary, control-heavy, empty, >1 MB, truncation; digest сверяется
  с `hashlib.sha256(data[:cap])`, текст — с `extract_plain_bytes(data[:cap])`.
- **Диагностика:** `AUTOFIND_SHOW_TIMINGS=1` заставляет CLI печатать постадийные `stats.timings`.

A/B на одном и том же 10k-корпусе, `--workers 4 --no-ocr`, только переключатель native:

| Замер | Pure Python | `afnative` | Эффект |
|---|---:|---:|---:|
| `read`, сумма по воркерам (2 прогона) | 3.74–3.96 с | 2.79–3.08 с | **−24%** |
| CLI internal throughput | 2665–2676 ф/с | 2904–3036 ф/с | **+8–11%** |
| subprocess wall time | 4.38–4.65 с | 3.84–4.30 с | **−7–10%** |

Остальные стадии (`store` 1.31–1.54 с, `embed` 1.08–1.23 с, `sha` 1.06–1.15 с,
`extract` 0.48–0.60 с, `scan` 0.45–0.51 с) в пределах шума не изменились. Итог всё ещё
ниже kensaku (4022 ф/с): следующий прирост потребует C-стороны для записи/chunking/embed
или полного C-side directory walker, что означает переписывание рабочего конвейера —
не делалось без явной просьбы и измерений.

`AutoFind.spec` подхватывает `afnative*.pyd` в `binaries` и добавляет hiddenimport только
если сборка расширения присутствует; без `.pyd` packaged-приложение работает на fallback.
PyInstaller 6.20.0 production build проверен: `AutoFind.spec` собирается успешно, `.pyd`
попадает в `_internal/afnative.cp313-win_amd64.pyd`. Повторная сборка в существующий
`dist/AutoFind` была остановлена safety-guard (313 файлов); финальная сборка сделана в
свежий `--distpath` без удаления прежнего dist.

## Финальный проход после запроса «дела»

Дальше measurements показали, что узкое место — не только `read`:

- **Sequential path** (`_index_one`, `--workers 1` или мертвый пул) всё ещё читал
  каждый plain-файл дважды и не вызывал native. Теперь он использует тот же
  one-read native путь, что воркеры: **52.8 с → 9.2 с** на 10k (189 → 1089 ф/с).
- **Авто-эвристика пула** брала 12 воркеров на 10k лёгких файлов; замеры 4/6/8/12
  показали оптимум 6, 12 проигрывали из-за spawn + памяти. Лимит снижен до 6
  для лёгких корпусов, 12 оставлен только при ≥16 тяжёлых файлов.
- **`cleanup_stale_artifacts`** спавнил `tasklist` ради live-PID (403 мс за вызов).
  Заменён на `EnumProcesses` через ctypes: **0.4 мс**, покрытие то же (разница —
  гонка с завершившимся процессом).
- **Части финализации** слиты: три `store.commit()` подряд заменены одним,
  `chunk_ids` берутся через `last_insert_rowid()` вместо SELECT по file_id.
- **Win32 reader**: добавлен `read_text_digest_win32()` (`CreateFileW` +
  `ReadFile`, `FILE_FLAG_SEQUENTIAL_SCAN`) как вариант по умолчанию; CRT-путь
  остаётся через `AUTOFIND_NATIVE_CRT=1`. A/B: CRT в среднем 3018 ф/с, Win32
  3066 ф/с (+1.6%, в пределах шума, но без регрессий). Оба reader-а проходят
  одинаковые 10 equivalence-тестов (20 subtests).
